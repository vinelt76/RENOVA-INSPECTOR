# Plan: Análisis de calidad de código y base de datos

## Objetivo
Crear `tasks_opencode/mimoanalisi.md` con un análisis completo del estado del código: calidad, mantenibilidad, y problemas de base de datos. Documento orientado a un primer proyecto serio.

## Hallazgos del análisis

### 1. ESTADO ACTUAL — Resumen ejecutivo

El proyecto tiene una **buena base arquitectónica** (separación de capas, cálculos puros con tests, schema definido) pero acumula deuda técnica en la capa de presentación y en la forma en que la DB se usa desde los componentes.

---

### 2. PROBLEMAS DE BASE DE DATOS (prioridad alta)

#### 2.1 Migraciones no versionadas
- `runMigrations()` en `sqlite.ts:66` ejecuta `CREATE TABLE IF NOT EXISTS` como un solo bloque gigante.
- **Riesgo**: si mañana agregás una columna, no hay forma de aplicar el cambio a tablas existentes. Necesitás un sistema de migraciones numeradas (v1, v2, v3...) con una tabla `schema_version`.
- **Impacto**: cuando la app esté en producción con datos reales, no vas a poder alterar el schema sin borrar la DB.

#### 2.2 Seed corre en TODA la inicialización
- `initApp()` en `sqlite.ts:179` llama `runMigrations()` + `runSeed()` siempre.
- `runSeed()` hace `INSERT OR IGNORE` en cada startup, lo cual funciona para demo pero:
  - Es lento en dispositivos reales (muchas queries secuenciales, ~50+ inserts).
  - No hay bandera "ya se sembró" — corre cada vez que la app arranca.
- **Solución**: agregar una tabla `app_meta` con `key/value` (ej: `seed_version = 1`) y solo sembrar si no existe o si la versión es menor.

#### 2.3 Duplicación de schema SQL
- El DDL de las tablas vive en **dos lugares**: `sqlite.ts:67-166` (inline en `runMigrations`) Y `schema.ts:104-227` (export `TABLE_SQL`).
- `TABLE_SQL` en schema.ts **no se usa en ningún lado** — es código muerto que puede divergir silenciosamente.
- **Solución**: eliminar `TABLE_SQL`, mantener una sola fuente (idealmente un archivo `migrations/`).

#### 2.4 Repo de inspección duplica cálculos
- `inspeccionRepo.ts:78-96` reimplementa el cálculo de RTD MOVI, IDI y estado RTD en línea, en vez de llamar a las funciones de `calculations.ts`.
- Hay un `try/catch` vacío que traga errores silenciosamente (`inspeccionRepo.ts:93-95`).
- **Riesgo**: si cambian las reglas en `calculations.ts`, el repo no se entera → cálculos inconsistentes entre seed y UI.
- **Solución**: importar y usar `calcularRtdMovi`, `calcularIdi`, `calcularEstadoRtd` directamente.

#### 2.5 Umbrales hardcodeados en repo
- `DEFAULT_RTD_CAMBIO = 4` y `DEFAULT_RTD_PROXIMO = 7` están en `inspeccionRepo.ts:8-9`.
- El CLAUDE.md dice explícitamente: "NUNCA hardcodear 4/7/8 ni %".
- **Solución**: estos valores deben venir de la empresa (tabla `empresa` o una tabla de configuración por empresa).

#### 2.6 persistDb() se llama en cada escritura
- Cada `upsert` en `unidadRepo`, `inspeccionRepo` llama `persistDb()` al final.
- En web, `saveToStore` es síncrono y costoso. En Android, es innecesario (SQLite ya persiste).
- **Solución**: debounce o persistir solo al final de una inspección completa, no en cada tecla.

#### 2.7 Query N+1 en seed
- `seedCatalogos()` en `seed.ts:117-127` hace un `SELECT` por cada modelo para obtener el `marca_id`.
- Con ~50 modelos, eso son 50 queries individuales. Podrían ser 1 sola query `SELECT id, lower(nombre) FROM cat_marca` y un lookup en memoria.

### 3. PROBLEMAS DE MANTENIBILIDAD / ARQUITECTURA

#### 3.1 Estilos inline masivos
- Todos los componentes (`EmpresaScreen`, `UnidadScreen`, `InspeccionScreen`, `FormBody`, `GrillaBody`) usan `style={{ ... }}` con objetos de 20+ propiedades.
- `EmpresaScreen.tsx` tiene ~139 líneas, cada una con estilos inline complejos.
- **Problema**: impossible refactorizar un botón sin tocar 15 objetos de estilo. No hay reuse de variantes (botón primario, secundario, etc.).
- **Solución**: pasar a CSS modules o Tailwind. Al mínimo, extraer `styles` objects a constantes reutilizables.

#### 3.2 Componentes muy grandes y con mucha responsabilidad
- `InspeccionScreen.tsx` (290 líneas) maneja: estado de posición, store de datos, catálogos, modos form/grilla, mapa de llantas, bottom sheets. Es el "god component".
- `GrillaBody.tsx` (228 líneas) duplica la lógica de `commit/upsert` que ya existe en `InspeccionScreen`.
- **Solución**: extraer sub-componentes (`PositionSelector`, `CatalogSheet`, `WheelMap`).

#### 3.3 StepDots duplicado
- La función `StepDots` está definida idénticamente en `EmpresaScreen.tsx:22-33` Y `UnidadScreen.tsx:10-21`.
- **Solución**: extraer a `src/components/StepDots.tsx`.

#### 3.4 Field helper duplicado
- La función `Field` y las constantes `labelStyle`/`selectBase` están duplicadas en `FormBody.tsx:5-10` y `GrillaBody.tsx:6-11`.
- **Solución**: extraer a `src/components/Field.tsx`.

#### 3.5 FormBody props excesivas
- `FormBody` recibe 17 props, incluyendo 5 refs. Es un signo de que el componente hace demasiado o los datos deberían agruparse.
- **Solución**: agrupar en objetos (ej: `refs: { codigo, r1, r2, r3, r4 }`, `catalogs: { marcas, modelos, ... }`).

#### 3.6 AppContext mezcla estado de sesión con estado de UI
- `AppContext` guarda `empresaId` (persistido en localStorage) junto con `unidadNumero`, `cabeceraId` (solo UI state).
- No hay separación entre "datos que sobreviven refresh" y "estado transitorio de la pantalla".
- **Solución**: separar en `SessionContext` (empresa, persistida) y `InspectionState` (unidad, cabecera, temporal).

#### 3.7 `empty()` definido en múltiples lugares
- `InspeccionScreen.tsx:11-15` define `empty()` y `GrillaBody.tsx:36-39` redefine la misma función.
- **Solución**: definir una sola vez en un archivo compartido o en schema.

#### 3.8 Archivos CSS muertos
- `App.css` (184 líneas) contiene estilos de template de Vite que no se usan en ningún componente.
- **Solución**: eliminar.

---

### 4. LO QUE ESTÁ BIEN (fortalezas)

- **Separación cálculos/UI**: `calculations.ts` es puro, sin side effects, con tests.
- **Schema bien definido**: interfaces TypeScript en `schema.ts` con tipos correctos.
- **Repo pattern**: capa de acceso a datos separada de la UI.
- **Uso de UUID**: IDs generados en dispositivo, listos para sync.
- **PersistDb**: ya pensado para web (jeep-sqlite) con fallback.
- **Seed data realista**: catálogo de patron + unidades demo.
- **StrictMode + memoización**: `initApp()` y `getDb()` están protegidos contra doble inicialización.
