# T08 — Paridad regla local (TS) vs regla SQL (Supabase)

**Método:** leer la definición real de `fn_rtd_state` y `fn_pressure_state_fixed` en producción
(`pg_get_functiondef`, solo lectura) y compararla con `calcularEstadoRtd`/`calcularEstadoPresion`
de `app/src/core/calculations.ts`.

## RTD: `fn_rtd_state` es fiel a la regla, pero usa umbrales VIGENTES, no históricos — ALTO

```sql
select case
  when p_rtd_mm is null then null
  when th.rtd_change_mm is null then null
  when p_rtd_mm <= th.rtd_change_mm then 'Para Reencauche'
  when p_rtd_mm <= th.rtd_next_mm  then 'Próximo a Reencauche'
  else 'Normal'
end
from (values (1)) dummy
left join lateral fn_effective_rtd_thresholds(p_company_id, p_size_name) th on true
```

La lógica secuencial (`≤ cambio` → `≤ próximo` → Normal) es **idéntica** a
`calcularEstadoRtd` — mismo orden, mismos límites inclusivos. Paridad de fórmula: correcta.

El problema no es la fórmula, es el umbral que usa: `fn_effective_rtd_thresholds(p_company_id,
p_size_name)` resuelve el umbral **de la empresa hoy**, consultado en el momento en que el
dashboard renderiza la fila — no el snapshot (`rtd_cambio_snap`/`rtd_proximo_snap`) que la app
calculó y capturó en el dispositivo al momento de la inspección. Esto es el mismo hallazgo de
T05 visto desde el lado SQL: la reproducibilidad histórica que `specs_fijas_vs_configurables.md`
documenta como ya resuelta ("Snapshot reproducible por fila... que viajan en `save_inspection`")
**no llega al dashboard**, porque ni se guarda el snapshot en `inspection_measurements` ni el
estado se calcula con él.

## Presión: `fn_pressure_state_fixed` usa un umbral plano 100/130 PSI, no la spec — ALTO (con matiz)

```sql
select case
  when p_psi is null then 'Sin Medir'
  when p_psi <= 100  then 'Baja Presión'
  when p_psi > 130   then 'Alta Presión'
  else 'Normal'
end
```

Contra `specs/reglas_negocio.md` §3, usando los ejemplos reales del propio Excel:

| Medida/eje | PSI | Spec (`calcularEstadoPresion`) | `fn_pressure_state_fixed` | ¿Coincide? |
|---|---|---|---|---|
| Dirección, ref 110 | 122 | Alta Presión (>116) | Normal (≤130) | **NO** |
| Tracción/Libre, ref 115 | 122 | Alta Presión (Excel: desde 122) | Normal (≤130) | **NO** |
| Dirección, ref 110 | 98 | Baja Presión (<99) | Baja Presión (≤100) | Sí (coincidencia) |
| cualquiera | 105 | depende de ref/eje | Normal | Depende |

Un neumático de eje Tracción a 122 PSI, que el propio Excel de referencia marca "Alta Presión",
se muestra "Normal" en el dashboard. La función ignora por completo `presion_ref` (110 vs 115
según medida/eje), `delta_alto_pct`, `delta_bajo_pct` y la tabla `umbral_presion` — coincide con
que `umbral_presion` está "INERTE" (`specs_fijas_vs_configurables.md`), pero deja ver que no es
solo inercia: hay una regla activa y diferente sirviendo datos al dashboard en su lugar.

**Matiz importante:** esto NO es un descubrimiento — `WEB/Inspecciones por unidad.html:794`
tiene el comentario explícito `// pressure_state_fixed: regla fija 100/130, calculada en la
vista`. El equipo sabe que es una regla provisional. Se reporta igual porque
`specs/reglas_negocio.md` dice explícitamente "si el código y este archivo difieren, el código
está mal", y esta es una divergencia real, verificada contra datos, que un fleet manager puede
estar leyendo mal hoy sin saber que la referencia real de su empresa/medida es distinta.
