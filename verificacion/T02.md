# T02 — Auditoría de `calculations.ts` contra `specs/reglas_negocio.md`

**Método:** lectura línea por línea de `app/src/core/calculations.ts` y
`reference/calculations.py` contra `specs/reglas_negocio.md` §1–§11, más los 48 casos de
`golden.json` (`verificacion/evidencia/T01-compare-golden.txt`).

## Resultado: paridad Python↔TS perfecta (48/48)

Las dos implementaciones son idénticas en comportamiento observable. El bug histórico no es
divergencia entre lenguajes — es divergencia entre ambas implementaciones y la spec, en tres
puntos, y un hallazgo adicional aguas abajo (persistencia) que ninguna suite existente cubre.

## Hallazgo 1 — `calcularIsaPeso` no puede expresar el peso 0 de "sin anomalía" — MEDIO

`specs/reglas_negocio.md` §6 define 3 niveles: desecho=5, anomalía sin desecho=1, **sin anomalía
(Normal)=0**. La firma actual es `calcularIsaPeso(desecho: boolean): number` — solo distingue
desecho de "no desecho"; no hay forma de pedirle el peso 0 porque no recibe si hubo anomalía.

Trazado hasta el llamador real, `app/src/db/repos/inspeccionRepo.ts:125-128`:

```ts
const desecho = await calcularDesecho(input.anomalia ?? null);
const isa_peso_snap = calcularIsaPeso(desecho === 1);
```

`input.anomalia` SÍ está disponible en ese punto (se usa una línea antes) pero no se pasa a
`calcularIsaPeso`. Resultado: **toda fila sin desecho recibe peso 1, incluidas las filas sin
ninguna anomalía**, que deberían pesar 0. `isa_peso_snap` ya se está escribiendo con este sesgo
en SQLite local hoy mismo, para cada inspección capturada.

Impacto real hoy: ninguno visible — el propio comentario del código (línea 127) documenta que
"ISA como score agregado NO está wireado a ningún flujo de UI todavía" (confirma
`specs/reglas_fijas_vs_configurables.md`). Impacto latente: el día que se conecte ISA a un
dashboard, el score saldrá inflado — cada neumático "Normal" pesará 1 en vez de 0 — y los datos
ya persistidos (`isa_peso_snap`) tendrían que recalcularse con retroactividad, no solo el código.

**No corregido en este recorrido** (afecta lógica de negocio, no es el import roto de T01).

## Hallazgo 2 — orden de evaluación en `calcularVur` no está impuesto por la spec — INFORMATIVO

`specs/reglas_negocio.md` §8 presenta 3 casos especiales como tabla, sin declarar prioridad
explícita entre "tasa nula/negativa → NULL" y "RTD ≤ rtd_cambio → 0". La implementación evalúa
la tasa primero: con `tasaAcumulada = null` y `rtdMovi ≤ rtdCambio` devuelve `null`
("sin datos suficientes"), no `0` ("cambio inmediato"). Es una lectura defendible de una tabla
que no fija orden — caso `vur-cambio-inmediato-sin-tasa` en `golden.json`, marcado
`spec_ambigua`. No se trata como defecto; se deja registrado por si el equipo de negocio prefiere
la lectura inversa (RTD en o bajo el límite manda "cambio inmediato" incluso sin tasa).

## Hallazgo 3 — `calcularIdi` no valida canales negativos — BAJO, sin impacto real

`calcularRtdMovi` rechaza canales negativos (`§1`); `calcularIdi` no repite la validación aunque
usa "los mismos canales". En la práctica no es alcanzable con datos reales: `inspeccionRepo.ts:114`
solo llama a ambas funciones bajo el mismo guard `canales.every(c => c >= 0)`, así que la app
nunca invoca `calcularIdi` con un canal negativo. Queda como hueco de la función pura en sí
(alguien podría llamarla directo, p. ej. desde un test o script futuro, y obtener un IDI de un
input inválido en silencio) — caso `idi-negativo-mismo-criterio-que-rtdmovi` en `golden.json`,
marcado `spec_ambigua`.

## Confirmado correcto

- `calcularRtdMovi`: MIN de canales medidos, D opcional en cualquier eje, rechaza negativos,
  no rechaza >22mm (solo la spec exige "advertencia", no bloqueo — correcto no implementarla
  aquí, es responsabilidad de la UI).
- `calcularEstadoRtd`: secuencial if/elif, límites inclusivos (`≤`) exactamente como §2.
- `calcularEstadoPresion`: secuencial, `sinMedir`/`null` primero, límites estrictos (`>`/`<`)
  como §3. Reproduce los 4 ejemplos del Excel salvo dos casos de redondeo de límite exacto
  (99.0 y 120.75) donde la fórmula (`>`/`<` estrictos) y la prosa del Excel ("desde X") pueden
  leerse distinto — ver `golden.json` casos `presion-dir-99-exacto` y
  `presion-trac-121-excel-dice-normal`, marcados `spec_ambigua`, no defecto de la función.
- `calcularVur`: casos "tasa 0/null→null", "RTD≤cambio→0", "tasa<0→null" todos correctos.
- `calcularTasaDesgaste`: `km_act == km_ant → null` correcto; permite tasa negativa (correcto,
  es la señal que VUR necesita para "dato inválido").
