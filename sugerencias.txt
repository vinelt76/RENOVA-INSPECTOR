### Qué va en cada capa (regla simple)

```mermaid
flowchart TB
    subgraph docs ["Documentación — leer antes de codear"]
```

## Reducción de tokens (aplicada en paso 4)

### 1. Capas de contexto — cargar solo lo necesario

El diseño de Claude ya apunta a **lazy loading**. En Cursor, replicarlo con reglas por carpeta:


| Sesión de trabajo | Contexto mínimo a incluir                                                   |
| ----------------- | --------------------------------------------------------------------------- |
| Cualquier tarea   | `CLAUDE.md` + `STATUS.md`                                                   |
| Motor de cálculo  | + `specs/reglas_negocio.md` secciones 1–4 + `decisions/0002-calc-parity.md` |
| Backend API/DB    | + `backend/CLAUDE.md` + ADR 0001                                            |
| Flutter UI        | + `mobile/CLAUDE.md` + `specs/flujo_inspeccion.md`                          |
| Planificación     | + `implementation_plan.md` (solo el sprint activo)                          |


**Regla de oro:** nunca adjuntar `implementation_plan.md` completo si la tarea es "implementar `calcular_rtd_movi`".

### 2. Recortar documentos gordos


| Acción                                                                                                           | Ahorro estimado                               |
| ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Mover [idea preliminar.md](idea%20preliminar.md) a `docs/archive/`                                               | ~1k tokens/sesión (evita duplicar CLAUDE.md)  |
| Extraer UX a `specs/flujo_inspeccion.md`; dejar en `implementation_plan.md` solo checklists por sprint con links | ~3k tokens cuando no trabajas en UX           |
| Crear `STATUS.md` (sprint, blockers, próximo paso)                                                               | Evita releer 400 líneas de plan               |
| ADRs 0003/0004 como docs de 30–50 líneas                                                                         | Evita re-explicar JWT y catálogo en cada chat |


### 3. `.cursorignore` — excluir lo pesado del indexado

```
# Excel y datos sensibles
**/*.xlsx
backend/tests/fixtures/
docs/archive/

# Build artifacts (cuando existan)
backend/.venv/
mobile/.dart_tool/
mobile/build/
```

El Excel **nunca** va al contexto del modelo. Solo el slice JSON derivado (~50 filas) para golden tests.

### 4. Reglas Cursor (`.cursor/rules/`)

Crear 2–3 reglas pequeñas en lugar de un mega-prompt:

- `00-proyecto.mdc` — stack cerrado, spec-first, español, no hardcodear umbrales (~30 líneas)
- `10-calculos.mdc` — "lee `@specs/reglas_negocio.md`; evaluación secuencial if/elif" (~15 líneas)
- `20-backend.mdc` — glob `backend/`**: row-level `empresa_id`, UUID cliente, golden test primero

Así Cursor inyecta contexto **automático y mínimo** según el archivo que editas.

### 5. Patrones de prompt (tú controlas ~70% del gasto)

**Mal (caro):**

> "Lee todos los documentos y empieza a codear"

**Bien (barato):**

> "Sprint 1 — implementa solo `backend/app/core/calculations.py` según `@specs/reglas_negocio.md` secciones 1–4. El golden test debe pasar contra `@backend/tests/fixtures/real_sample.xlsx`. No toques endpoints."

Otros hábitos:

- **Una tarea = un módulo** (calculations → golden test → models → sync endpoint)
- **Citar paths con `@`** en lugar de pegar contenido
- **No re-adjuntar** specs ya en el repo; el agente las lee bajo demanda
- **Cerrar decisiones abiertas** (presión CALIENTE, JWT offline) en ADRs antes de codear — evita loops de "¿cómo lo hacemos?"

### 6. Fixtures derivados vs Excel crudo


| Artefacto          | Uso                                  | Tamaño                 |
| ------------------ | ------------------------------------ | ---------------------- |
| `real_sample.xlsx` | Generación manual, local             | Grande — gitignored    |
| `real_sample.json` | Golden test Dart + referencia Python | ~50 filas, commiteable |
| CSV en fixtures    | Alternativa ligera al xlsx           | Mínimo                 |


Convertir Excel → JSON **una vez**; en adelante la IA solo ve JSON.

### Claude vs Cursor — cuándo usar cada uno


| Herramienta              | Mejor para                                                                                             | Contexto mínimo                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| **Claude** (chat aparte) | Validar lógica de negocio, discutir casos del Excel, redactar ADRs, revisar propuestas antes de codear | Pegar solo § de `reglas_negocio.md` + 2–3 filas del Excel    |
| **Cursor** (aquí)        | Escribir código, correr pytest/flutter test, scaffolding, reglas `.cursor/`                            | `@specs/reglas_negocio.md` + `@STATUS.md` + archivo concreto |


**Flujo recomendado:**

1. Claude → propuesta + casos de prueba (Fase 2–3)
2. Tú → OK o correcciones
3. Cursor → implementación + tests (Fase 4)
4. Tú → corres `pytest` y confirmas
5. Actualizas `STATUS.md` (Fase 5)

Así Claude no necesita ver todo el repo; Cursor no reinterpreta la lógica sin tu filtro previo.
